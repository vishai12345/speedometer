    Design

    Data flows in one direction. The sensor runs at about 1 Hz while the screen runs at 60 fps, so the two are decoupled: fixes update the estimate, and the render loop animates toward it.

    • SI units inside. All maths runs in metres and seconds. Units are converted only at display time, so switching km/h ↔ mph never corrupts trip data.
    • One state object. Sources write to it, the render loop reads from it. No component talks to another directly, so sources are swappable (GPS, simulator, or an OBD-II adapter later).
    • Canvas for the dial, DOM for text. The dial redraws every frame on a devicePixelRatio-scaled canvas; numbers stay as real text so they are crisp, selectable and readable by screen readers.
    • Accessible at sensor rate. A polite live region announces speed every few seconds, not 60 times a second.
    • Swappable faces. Each display style is one draw function reading the same state, so adding a new face never touches the sensor or filter code.
    • Theme-aware. The canvas reads its colours from CSS tokens, so light and dark mode match the rest of the page.

    Working principle

    1. Measuring speed

    A phone GNSS chip measures speed from the Doppler shift of satellite signals and exposes it as coords.speed in m/s. This is far more accurate (typically 0.1–0.5 m/s) than differencing positions, because position error is several metres per fix. When speed is null, the app falls back to distance between two fixes divided by elapsed time, using the haversine formula:

    a = sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2) d = 2R · atan2(√a, √(1−a)) R = 6 371 000 m v = d / Δt

    2. Filtering noise

    Raw readings jitter. A one-dimensional Kalman filter models speed as a random walk driven by acceleration noise σa, and weights each reading by its uncertainty r (derived from the reported accuracy):

    predict: P ← P + σa² · Δt² gain: K = P / (P + r) update: v ← v + K · (z − v) P ← (1 − K) · P

    Good fixes (small r) move the estimate quickly; poor fixes barely nudge it. Fixes with accuracy worse than 50 m are rejected outright.

    3. Moving the needle

    The estimate changes once per fix, which would make the needle jump. The render loop drives the needle with a critically damped spring, which settles fast with no overshoot:

    a = ω² · (target − x) − 2ω · ẋ ω = 6 rad/s ẋ ← ẋ + a · Δt x ← x + ẋ · Δt

    4. Trip maths

    Distance integrates the filtered speed each frame (d += v·Δt), counting only above 0.5 m/s so GPS drift while parked adds nothing. Average speed is distance over moving time, matching how car trip computers report it.

    Implementation

    1. Scaffold one HTML file with a square container holding a <canvas> and an overlaid text readout. Serve it over HTTPS; browsers expose geolocation only in secure contexts.
    2. Write the sensor adapter. Wrap watchPosition with enableHighAccuracy: true and maximumAge: 0. Map each position to {t, lat, lon, acc, speed}. Handle error code 1 (denied) by switching to the simulator, and codes 2 and 3 by showing a "waiting for fix" state. 
      watchPosition(p => onFix({
  t: p.timestamp, lat: p.coords.latitude, lon: p.coords.longitude,
  acc: p.coords.accuracy, speed: p.coords.speed
}), onError, { enableHighAccuracy: true, maximumAge: 0, timeout: 15000 });
    3. Validate fixes. Drop accuracy > 50 m, Δt < 0.5 s for differenced speeds, and anything above 90 m/s (324 km/h).
    4. Add the Kalman filter. 
      class SpeedKalman {
  constructor(sigmaA = 1.2) { this.sa2 = sigmaA ** 2; this.reset(); }
  reset() { this.x = 0; this.P = 25; this.t = null; }
  update(z, r, t) {
    if (this.t === null) { this.x = z; this.P = r; this.t = t; return z; }
    const dt = Math.min(Math.max((t - this.t) / 1000, 0.001), 10);
    this.t = t;
    this.P += this.sa2 * dt * dt;
    const K = this.P / (this.P + r);
    this.x = Math.max(0, this.x + K * (z - this.x));
    this.P *= 1 - K;
    return this.x;
  }
}
    5. Add the haversine fallback for devices that report speed: null; set r from the combined accuracy of both fixes divided by Δt.
    6. Build the render loop with requestAnimationFrame, clamping Δt to 50 ms so a backgrounded tab doesn't fling the needle when it returns. 
      const w = 6;
const acc = w*w*(target - x) - 2*w*v;
v += acc * dt; x += v * dt;
    7. Draw the dial. Size the canvas with a ResizeObserver to clientWidth × devicePixelRatio. Use a 270° sweep starting at 135°; map speed to angle with start + sweep · v / max. Draw the track, the over-limit band, the progress arc, minor and major ticks with labels, then the needle and hub.
    8. Add the trip computer and sparkline. Integrate distance per frame, sample speed every 500 ms into a 120-point ring buffer and plot it with the limit as a dashed line.
    9. Add alerts. When the needle passes the limit, set an .over class for the red state and play a short Web Audio tone every 1.5 s. Start audio only after a tap, as browsers require.
    10. Persist settings and hold the screen. Save units and limit to localStorage inside try/catch. Request navigator.wakeLock.request('screen') and re-request it on visibilitychange.
    11. Test with the simulator, which runs a city–highway–overspeed–braking cycle with Gaussian noise, then test on a real phone outdoors with a clear sky view.

    Deploy

    The whole app is one self-contained index.html with no build step and no backend. Location data never leaves the device.

    1. Rename the downloaded file to index.html.
    2. Host it on any HTTPS static host: drag it onto Netlify Drop, push it to a GitHub Pages repo, or run npx vercel in its folder.
    3. Open the HTTPS address on your phone, choose Device GPS and allow location.
    4. Optional: add a web app manifest and a service worker so it installs to the home screen and works offline.

    Production checklist

    • HTTPS only; geolocation is blocked on plain HTTP.
    • Ask for location from a button tap, never on page load, so permission prompts have context.
    • Show signal state at all times: waiting, weak (accuracy shown), lost after 5 s without a fix.
    • iOS Safari pauses location when the screen locks; the wake lock keeps it running.
    • GPS speed lags reality by roughly 0.5–1 s. Treat this as a driver aid, not a calibrated instrument.
